# Decisions

Choices the brief (`SPEC.md`) doesn't make, with the reasoning. Newest at the bottom. Raise anything here in review; nothing is expensive to undo yet.

## Phase 0

1. **Prisma 6, not 7.** Prisma 7 requires driver adapters and a `prisma.config.ts`; switching database then means swapping an adapter in code. Prisma 6 keeps the "boring" setup the brief describes: `DATABASE_URL` in `.env`, `file:./dev.db` in dev. Moving to Postgres is one line in `prisma/schema.prisma` (`provider = "postgresql"`) plus the URL. No dialect-specific attributes are used.
2. **Prisma enums are used for every status field** (validated on SQLite with `prisma validate` and the init migration). They map to `TEXT` on SQLite and native enums on Postgres with no schema edits.
3. **Schema additions beyond spec section 4**, all nullable or defaulted:
   - `BankAccount.userId` is nullable so organisation accounts can exist without a user (Organisation → BankAccount).
   - `BankAccount.changedAt` drives the 24h receiving cooling-off.
   - `Payment.payerUserId` is nullable and `Payment.payerDisplayName` exists for people who pay a collection from the public web page without an account.
   - `PaymentRequest.lastRemindedAt` backs the once-per-24h reminder rate limit.
   - `User.deletedAt`, `User.phoneE164`/`phoneHash` nullable: account deletion blanks the phone fields and keeps the row so `Payment` history can be anonymised rather than deleted.
   - `OtpChallenge.consumedAt`, `Session.lastUsedAt`: bookkeeping.
4. **Endpoints the UI needs that section 5 doesn't list** (to confirm in Phase 1): `GET /me` returns the profile, a bank *summary* (bank name, CoP status, cooling-off end; never account identifiers) and the current limits; `GET /requests?role=incoming|outgoing`; `GET /orgs` returns organisations with collection summaries. List responses use an envelope (`{ "payments": [...] }`) so metadata can be added later. Payments carry a `counterparty { userId, displayName }` so the feed can render without a second lookup.
5. **Limits live in `backend/src/limits.ts`** and are returned by `GET /me`, so the app shows what the server enforces instead of hard-coding them.
6. **Fastify's logger is configured with options**, not a pino instance: Fastify 5.12's `loggerInstance` type does not accept pino 10's `Logger`. Services receive `app.log` (or a child) as a parameter.
7. **vitest 4.0.18.** vitest 5 requires Node 22 (the brief says Node 20); vitest 4.1 trips an npm 10 peer-resolution bug that breaks a clean `npm ci`.
8. **Xcode project is hand-written** using Xcode 16's file-system-synchronized groups, so adding a Swift file to a folder adds it to the target with no project edits. No XcodeGen. Bundle identifier placeholder: `com.quid.app`.
9. **Two shared schemes:** `QuidApp` (live backend at `localhost:3000`) and `QuidApp-Mock` (`-mock` launch argument). `QUID_API_BASE_URL` overrides the base URL.
10. **MockMode is a `URLProtocol`**, not a second client. The real `APIClient`, JSON decoding and error mapping run in the demo and in tests; only the transport is faked. Fixtures build dates relative to "now" so Today/Yesterday grouping stays realistic.
11. **The app's entry type is `QuidMain`**, not `QuidApp`, so a type never shadows the module name (`QuidApp.Foo`).
12. **Design tokens not in the brief:** failure tint `#FBE8E6` / text `#9A2B1F`; cards are white (`#FFFFFF`) on the `#F6F7F5` background; a secondary fill `#EEF1EF` for secondary buttons and icon tiles. In dark mode surfaces invert and the accent fill stays `#0B6B54`; small accent *text* lightens to `#6CCBAA` to keep 4.5:1 contrast. Letter-spacing is −2 on hero/large amounts and −0.5 on inline amounts (−2 is unreadable at 17pt).
13. **Avatar tints** are six muted background/foreground pairs chosen by a stable FNV hash of the name, so a person keeps their colour across launches and screens.
14. **`NSAllowsLocalNetworking`** is set so the live scheme can reach `http://localhost:3000` on the simulator without disabling App Transport Security generally.
15. **Phase 0 includes a UI shell** for the four tabs on canned data (slightly beyond "scaffold") so the design system could be reviewed as real screens. Later-phase actions open a "Phase N" sheet rather than silently doing nothing.
16. **Repo-root scripts are shell wrappers** that `cd backend`; a TypeScript file in `/scripts` could not resolve `@prisma/client` from `backend/node_modules`.
17. **Legal URLs** are placeholders (`https://quid.example/...`) until real pages exist.

## Phase 0 review fixes

An adversarial review (four lenses, each finding challenged by a skeptic) ran before hand-off; 21 findings were confirmed and fixed. Decisions that came out of it:

18. **System chrome is tinted with `quidAccentText`**, not `quidAccent`: the selected tab, back buttons, toggles, progress bars and the loading spinner need 4.5:1 against dark surfaces, and `#0B6B54` only manages about 2.8:1 there. Filled buttons keep `quidAccent` because their foreground is white (6.5:1). The asset catalog's AccentColor has the same dark-appearance value so UIKit alerts match.
19. **Activity, Collect and Me are card stacks, not `List`s.** `insetGrouped` lists force 10pt corners and SF section headers, which broke the one visual language across tabs. Rows that push a screen draw their own chevron (`QuidChevron`). Navigation titles and segmented controls are set to Manrope via `UIAppearance` (`QuidAppearance.configure()`), scaled with `UIFontMetrics` for the current text size. Appearance proxies are static, so `RootView` re-runs `configure()` when the text size changes mid-session: bars created from then on use the new size, bars already on screen keep theirs until they are recreated (SwiftUI content scales live either way). Rebuilding the tab hierarchy to force it was tried and rejected because it discarded tab selection, loaded data and search state. Known limitation for the Phase 5 accessibility audit. Rows that leave the app (Legal) show an external-link glyph, not a chevron.
20. **Section headers are 44pt tall** so a trailing text action ("See all") always has a full-size hit target; small headers (day groups, settings groups) are 13pt muted Manrope.
21. **Task cancellation is not an error.** `APIClient` turns `URLError.cancelled` into `CancellationError`, and every ViewModel's `load()` returns quietly on it. Switching tabs mid-load no longer flashes a "cancelled" error card.
22. **Loading placeholders are driven by a first-load state, never by "data is nil".** Each ViewModel (Home, Activity, Collect, CollectionDetail, Me) exposes `hasLoaded` and `isAwaitingFirstLoad` (nothing loaded yet and nothing failed), which also covers the first frame before `.task` runs and a load cancelled by leaving the tab. Home's inline recent-contacts line switches to error wording only when the first load failed (`!hasLoaded && error != nil`); a failed refresh with contacts already on screen keeps the neutral text. List sections that own a retry card (Home activity, Activity, Collect, collection detail) show that card whenever a load fails and no items are on screen, including after a successful empty first load, since retry is the right offer in that state. A failed first load shows an error card with retry that stays mounted while the retry runs; `error` is cleared only on success. Account-deletion failures surface in their own alert (`deleteError`) rather than being swallowed.
23. **Pretty logs are an explicit opt-in** (`LOG_PRETTY=1` or `true`; blank, `0` and `false` mean off). `pino-pretty` is a devDependency, so keying it off `NODE_ENV=development` crashed a production start with no fatal log line. `server.ts` imports config, the database module and the app dynamically inside `main()` in that order, so environment validation runs before Prisma Client is constructed, and validation, logger construction and listen failures all go through the one `failed to start` handler.
24. **Log redaction uses explicit paths** (`phone`, `*.phone`, `req.body.phone`, …) generated from one `SENSITIVE_FIELDS` list, and `err.code` is deliberately visible. A test logs representative shapes and asserts exactly what is censored. Add a path when you log a new shape; pino's `*` matches one level only.
25. **The test database is recreated on every `npm test`** and test files run sequentially (`fileParallelism: false`), since they share one SQLite file. The Prisma CLI is invoked via `process.execPath`, which also works on Windows.
26. **`Package.resolved` is committed** (the ignore rule was removed) so Phase 2's SPM dependency on the TrueLayer SDK stays reproducible.
27. **Secondary buttons have a visible pressed state** (`quidSurfaceSecondaryPressed`, `#DFE4E1` light / `#323C37` dark); the previous pressed colour was indistinguishable from resting.
28. **Section headers carry the VoiceOver header trait** so the Headings rotor can jump between day groups, settings groups and organisations now that those screens are cards rather than `List` sections.

## Phase 1

29. **Two-layer phone hashing.** The brief says the app sends hashes, never numbers, and that the pepper lives in `.env`; a server-only pepper means the app cannot compute an HMAC. So the app sends `clientHash = SHA-256(E.164)` (unkeyed; transport hygiene, not a secret, since the number space is small) and the server stores and matches `HMAC-SHA256(pepper, clientHash)`. The pepper protects the hash column in isolation (lookup logs, partial exports) and stops clients precomputing server hashes; it does not hide numbers from someone holding the whole database, because `User.phoneE164` is a plaintext column by the brief's own schema (section 4). The shared test vector for `+447700900123` is `a8acc3a9…1436` on both sides.
30. **OTP.** Six digits from a CSPRNG, HMAC-hashed with the pepper and bound to the phone number, 5-minute TTL, 5 attempts then locked, the newest code supersedes any open one. Per number: 5 codes per 15 minutes. Per IP: 30 auth requests a minute. `/auth/otp/start` answers identically for registered and unregistered numbers, so it cannot probe the directory. Dev mode logs the SMS body as `{ sms: { to: "+44 ***123", body } }` (spec section 5: the code is logged, not sent); the mask keeps only the last three digits, and `req.body.code` stays redacted. Attempts are claimed with a conditional atomic increment *before* the code is compared, so twenty simultaneous guesses still stop at five, and the successful consume is conditional too, so one code mints exactly one session.
31. **Sessions.** 32 random bytes as a base64url bearer token; only its SHA-256 is stored; 30-day TTL (`SESSION_TTL_DAYS`); `lastUsedAt` refreshed at most hourly. `POST /auth/logout` deletes that one session. Expired sessions and deleted users get 401. Keychain holds the token on the phone, memory in MockMode.
32. **Dev stand-ins are refused in production.** `SMS_SENDER=log`, `COP_VERIFIER=fake`, the placeholder pepper and the all-zero key each abort startup when `NODE_ENV=production`.
33. **Confirmation of Payee flow.** `PUT /me/bank-account` runs the verifier first. MATCH stores the details (AES-256-GCM) and answers with the bank summary; CLOSE_MATCH stores nothing and returns the bank's version of the name for the user to accept (the app resubmits with it); NO_MATCH stores nothing. `FakePayeeVerifier` fixtures: sort code `999999` is NO_MATCH; the registry accounts `04-00-04 12345678` (Sam Okafor), `04-00-04 87654321` (Priya Patel) and `23-05-80 11223344` (SOAS Hockey Club) are MATCH only with that exact name and CLOSE_MATCH when it differs by case or spacing; anything else is MATCH so any dev account can be linked.
34. **Providers are a static GB list in Phase 1** (`services/providers.ts`) with TrueLayer-style ids such as `ob-monzo` and no logos; the sandbox mock bank is included when `TRUELAYER_ENV=sandbox`. Phase 2 replaces the source with the TrueLayer providers API (cached 1h) after reading its docs, validates the ids and migrates stored `providerId`s if any differ.
35. **Cooling-off starts on a change, not the first link.** `BankAccount.changedAt` is compared with `createdAt`; `GET /me` reports `coolingOffUntil` only within 24h of a change. Enforcement against payments is Phase 5.
36. **`DELETE /me` ships in Phase 1** (the brief lists it under Phase 5) because the Me screen already offers it: sessions and bank details are deleted, phone fields blanked, the name becomes "Deleted user", `deletedAt` is set, and the number can sign up again as a new user. Anonymisation of `Payment` rows is asserted in Phase 5 once payments exist.
37. **Directory lookup** dedupes hashes, excludes the caller and deleted users, and is limited to 10 requests a minute per user by a limiter that runs *after* auth (`app.rateLimit()` as a preHandler) so it keys on the user id rather than the IP.
38. **`GET /requests` and `GET /orgs` return empty lists** until Phases 3 and 4, so the live app's tabs show real empty states.
39. **Bank linking is skippable** during onboarding ("I'll do this later"). The skip is a per-device flag; Home then shows a "Link your bank to get paid" card and Me offers the same sheet. Linking from either clears the flag.
40. **Onboarding resumes from the profile**, not from device state: after sign-in, `GET /me` decides the next step (empty name, then bank unless skipped, then the contacts explainer flag). `AppEnvironment.onboardingInProgress` keeps the flow on screen while the session appears mid-way, so a verified code does not bounce the user to a loading screen.
41. **Contacts permission is not requested in Phase 1.** The explainer screen describes hashing and defers the system prompt to the first Pay tap (Phase 2), as the brief requires. `ContactsService`, `UKPhone` and `DirectoryService` are built and tested now.
42. **The mock backend is stateful.** `-signed-out` launches on the welcome screen with a fresh mock user; the accepted code is `123456`; sort code `999999` is NO_MATCH and an all-lowercase holder name is CLOSE_MATCH; the directory recognises the demo contacts' numbers. The onboarding XCUITest runs against this.
43. **UK phone normalisation** lives in one function on each side (`lib/phone.ts`, `UKPhone.swift`) with the same table of accepted inputs, because the directory only works if both sides hash exactly the same string.
44. **Encrypted fields are bound to their owner and column.** `encryptField(plaintext, aad)` uses AES-GCM associated data `user:<id>:<column>` and a leading format-version byte, so a ciphertext copied into another row or column fails to decrypt, and `BANK_DATA_KEY` can later be rotated by re-encrypting in place. Only `services/bankAccounts.ts` (and payment creation in Phase 2) ever decrypts.
45. **Cooling-off starts only when the sort code or account number actually change.** The bank-account service decrypts the stored identifiers to compare; re-verifying the same account, fixing the holder name or choosing a bank leaves `changedAt` alone. `coolingOffUntil` is derived from `changedAt > createdAt`, both set to the same instant on first link.
46. **Bank verifications are capped at 10 per user per hour** (`LIMITS.bankVerificationsPerHour`): Confirmation of Payee is an external, per-call-billed service that discloses the bank's version of a name on CLOSE_MATCH. One log line per attempt carries `{ userId, copStatus }` only.
47. **Deleting an account also deletes that number's one-time-code rows**, and `purgeExpired()` removes challenges an hour past expiry and sessions past their TTL at startup and hourly, so plaintext numbers and dead token hashes do not accumulate.
48. **Any authenticated call answered 401 ends the session on the device.** `APIClient` clears the token store and tells `SessionStore`, so RootView returns to Welcome instead of leaving error cards on every tab. Sessions are a fixed 30 days (no sliding refresh) until there is a reason to change that.
49. **Provider list hygiene.** The Metro Bank row carried a wrong id and was removed; the remaining ids follow TrueLayer's `ob-<bank>` convention from memory and are explicitly unverified until Phase 2 reads the providers API, which must validate every stored `providerId` before any preselected payment is created.
50. **The signed-in demo user counts as onboarded for that launch only.** `AppEnvironment.demo(signedIn: true)` and "Explore the demo" set the in-memory contacts-explainer flag without touching UserDefaults, so a fresh simulator lands on the tabs (the UI test depends on this) while a live sign-in on the same device still sees the explainer once. A reinstall of a real account shows the explainer again by design: that is where contacts permission is re-explained.
51. **Per-IP auth caps are per route and the one limit `buildApp` lets tests tune.** `@fastify/rate-limit` counts each route separately, so the 30/min cap applies to `/auth/otp/start` and `/auth/otp/verify` independently. Every injected test request comes from 127.0.0.1, so the shared test app lifts the cap to 10,000 and one dedicated test builds an app with a cap of 3 to prove the limiter is wired.
52. **Never reassign an `@Observable` property inside its own `didSet` without an equality guard.** The macro moves the observer onto the generated `_name` storage, so `code = cleaned` inside `didSet` goes through the public setter and fires the observer again without end; the Phase 1 build crashed with a stack overflow the moment `submitPhone` cleared `code` (and the unit-test host crashed the same way, which xcodebuild hid by relaunching it). Every filtering observer now reads `let cleaned = …; if cleaned != value { value = cleaned }`, CI fails on a test-host crash, and a unit test drives each of these fields.
53. **Linking a bank refreshes the profile before clearing the skip flag, and a 401 forgets the whole device state.** `bankAccountLinked()` awaits `loadProfile()` and only clears `bankLinkSkipped` when the profile shows the account, so RootView never derives "no bank, not skipped" and bounces a Home/Me link back into the onboarding bank step. Any 401 now routes through `sessionEnded()`, which does what sign-out does locally (session, profile, `onboardingInProgress`, per-device flags) so a session that dies mid-onboarding lands on Welcome instead of a dead end.
54. **`TRUST_PROXY` is off by default and never `true`.** Behind ngrok or a load balancer every client arrives from the proxy's address and the per-IP auth caps collapse into one bucket; `TRUST_PROXY=1` (hop count) or an address list makes Fastify read `X-Forwarded-For`. `true` is refused at startup because the leftmost header value is client-controlled and would let a caller pick their own bucket.
55. **"Registered" in the directory means a named account.** `/directory/lookup` skips users with an empty `displayName` (code verified, onboarding never finished) so the Phase 2 picker never shows a nameless "on Quid" entry. A skipped bank link does not exclude anyone: payability is enforced at payment time (SPEC section 7), not by the directory.
56. **The phone field never drops digits from international input.** The as-you-type formatter used to cut "+447700900123" to 11 digits, which `normalise` then accepted as a *different* valid number, so the code would have gone to a stranger. Input starting with `+`, `0044` or `44` now keeps the country code ("+44 7700 900123"); national input keeps the 11-digit cap.
57. **A first-time bank link that loses the unique(userId) race falls back to the update path** (Prisma P2002) instead of a 500, so a retry after a timeout or a second device sees 200 and the single stored row; the cooling-off rule is unaffected because the identifiers match.
58. **Review follow-ups landed in Phase 1:** CoP result pages show a failed re-verification inline and the MATCH Continue button carries a loading state; going back from the code step clears its error; the OTP error is announced to VoiceOver; the skip link has a full-width 44pt target; the bank sheet says "Link" or "Change" from the profile; provider initials scale down instead of overflowing; the Terms and Privacy names are links; focus moves from sort code to account number to name as each is completed, since the number pads have no Next key.
59. **TrueLayer docs were unreachable while Phase 2 was built, so every unverified shape lives in one place.** docs.truelayer.com, api.truelayer-sandbox.com and auth.truelayer-sandbox.com are denied by the cloud environment's network policy. Verified instead from TrueLayer's official sources: request signing and the `Tl-Signature`/`Idempotency-Key` headers, the sandbox API host, the `/v3` prefix, webhook signature verification including the `jku` allowlist (`truelayer-signing` repo and npm 0.2.3, whose shared test resources are committed under `backend/test/fixtures/truelayer`); the iOS SDK package URL, version 4.1.9 and its `processSinglePayment`/`configure` API (TrueLayer-iOS-SDK repo, read from the binary's swiftinterface). Also verified, from two recorded sandbox webhooks in the same repository: Payments webhooks are flat (`type`, `event_version`, `event_id`, `payment_id`, `failure_reason`/`failure_stage`), executed events carry the payer's account identifiers under `payment_source`, and `mock-payments-gb-redirect` is a real provider id. Still to check on docs.truelayer.com before the first sandbox run: the token endpoint and scope, every field of the create-payment body and response, the `GET /v3/payments/{id}` fields, the raw status vocabulary, the full webhook event list (`payment_settled`, `payment_authorized`), whether retried deliveries carry a fresh `X-Tl-Webhook-Timestamp`, whether `payment_settled` is emitted for external-account beneficiaries, whether the hosted payment page appends `payment_id` to the `return_uri` and accepts our own `https://<domain>/c/return` for people paying a collection link (Phase 4), the Idempotency-Key replay semantics (no retry is attempted until known), the hosted payment page URL, and the GB provider ids in `services/providers.ts` (decisions 34 and 49 stay open; link "Mock Bank (sandbox)" before paying in the sandbox). They are isolated in `backend/src/services/truelayer/client.ts` and `webhooks.ts`, each with a header comment; a mismatch fails loudly (unknown status, 4xx from TrueLayer, FAILED + 502) rather than corrupting data, and `npm run smoke` is the first thing to run once the hosts are allowed. Phase 5 adds the cancel action, known only from search results of TrueLayer's cancel-a-payment page (docs.truelayer.com still did not resolve): `POST /v3/payments/{id}/actions/cancel`, an empty 202, and the outcome later as `payment_failed` with `failure_reason` `canceled` or as `payment_cancellation_failed`; the signed `{}` body and a fresh Idempotency-Key per attempt are assumptions. The same results show `mock-payments-gb-redirect` displayed as "Mock UK Payments - Redirect Flow", its approval page on pay-mock-connect.truelayer-sandbox.com, and the hosted payment page on payment.truelayer-sandbox.com, matching the default in `truelayerHosts()`.
60. **Payment statuses are a ranked ladder with one gate.** CREATED → AUTHORIZING → AUTHORIZED → EXECUTED → SETTLED; FAILED and CANCELLED from anything before EXECUTED (the split is informational: pill text and copy; limits, polling and the result screen treat them alike, so a cancel-worded failure reported after authorisation still ends the payment). `applyTransition` is the sole writer: a repeated status is a duplicate, a lower-ranked status after a higher one (executed after settled) is stale and logged quietly, anything after a failure or that would fail an executed payment warns and is ignored. Provider "failed" with a cancellation reason maps to CANCELLED. Webhooks and the poll both go through it, so order of arrival cannot matter.
61. **Limits count payments still in flight, and creation is serialised per payer.** The rolling 24h/30d sums include CREATED/AUTHORIZING/AUTHORIZED payments, so parallel requests cannot pass the check together; a payment the bank never completes stops counting when the poll marks it FAILED, and a CREATED row that never reached the provider (the process died mid-call) is failed as `abandoned` after ten minutes by the same tick, since nobody holds a token for it. The check and the CREATED insert run under an in-process lock keyed by payer (SQLite interactive transactions proved unreliable under contention). A multi-instance Postgres deployment needs a row lock on the payer there instead: on the Phase 5 go-live checklist.
62. **`PAYMENT_PROVIDER=fake` is a development stand-in, not the sandbox.** It keeps payments in memory, serves a plain-HTML approval page at `/dev/authorise/<id>` that moves the payment through authorized → executed → settled and reconciles our row at once, and is refused in production like the SMS and CoP stand-ins. It exists so the whole app → bank → app loop can be exercised with no TrueLayer credentials; `POST /payments` says `provider: "fake"` and the app then opens that page in a web session instead of the SDK.
63. **What a payer learns about a payee.** `POST /payments` returns the payee's account-holder name as their bank confirmed it only when `firstTimePayee` is true (and nowhere else), because the first-time-payee warning in SPEC section 7 is the one case the spec carves out of section 4's "never returned to any client"; the order POST → sheet → authorisation follows screen 3, so a Cancel on the sheet leaves a provider payment that expires unpaid. A per-user cap on distinct new payees per day (against enumerating names at a penny each) and an audit line per disclosure go on the Phase 5 list. `/directory/lookup` adds `bankName`, `canReceive` and `coolingOffUntil` per registered contact so the picker can say who can be paid now; account identifiers never leave the server.
64. **Webhooks answer 200 once the signature is good.** Unsigned or tampered deliveries get 403; after verification, duplicates (by `event_id`, stored in `WebhookEvent`), unknown payments and unhandled event types are acknowledged with 200 so TrueLayer stops retrying; only a database failure yields a 5xx. The timestamp's age is logged at warn beyond five minutes but never enforced: replay is already a no-op through `event_id` and the forward-only state machine, and whether retries are re-stamped is unverified. The event row is written after the transition, so a failure between the two leaves no row and the retry applies the event; a unique-violation on that final insert is a concurrent copy and is acknowledged. The `jku` must be one of TrueLayer's two JWKS URLs for the configured environment and the key set is cached per URL. Webhook bodies carry the payer's account identifiers, so no handler logs a body.
65. **Bank authorisation on iOS is the SDK first, the hosted page as a fallback, a stand-in in MockMode.** The SDK's own result screen is switched off so Quid's server-driven result screen is the only one; the SDK is re-invoked with the same context when `quid://return/payment` arrives, as its documentation recommends. `QUID_HOSTED_PAGE=1` in the scheme forces the web session for debugging. The SDK is a binary Swift package resolved from GitHub at build time (`TrueLayerSDK`, exact 4.1.9).
66. **The result screen trusts the server, not the bank's screen.** It polls `GET /payments/:id` every 3 s for 60 s and shows Paid only for EXECUTED/SETTLED; a cancellation or failure reported by the authoriser is shown as Failed with "Try again" while polling continues in case the server disagrees. Cancelling the first-time-payee sheet leaves the CREATED/AUTHORIZING payment on the server to expire through the provider and the poll; nothing has been sent, but the amount counts against the payer's rolling limits until the provider expires it or the fallback poll sees a terminal status (the abandoned-creation sweep in #61 only covers rows that never reached the provider). A payer-initiated cancel endpoint (`POST /payments/:id/cancel` while the payment is still before EXECUTED) is on the Phase 5 list so the app can release the amount at once.
67. **Contacts behind an interface.** `ContactSource` wraps the address book so MockMode and tests use six canned contacts with no permission prompt; the system prompt is requested from the picker, with inline cards for "not yet asked" and "denied" (Open Settings). Contacts not on Quid get an Invite button that shares a message with a placeholder link until Phase 3 brings real invite links.
68. **Amount and reference rules are enforced on both sides.** The keypad allows at most five pounds digits and two decimals; the reference is filtered to letters, digits, space and `& . / -` and cut at 18 characters as typed, defaulting to "From <first name>"; the server rejects anything else with `invalid_reference`. Errors from the server (`limit_24h`, `payee_cooling_off`, `payee_not_payable`) are shown inline on the amount screen with the server's own sentence.
69. **Section 7 enforcement ships with `POST /payments` in Phase 2, not Phase 5.** SPEC 5 defines the endpoint as validating section 7 and screen 3 puts the first-time sheet in the pay flow, so the rolling limits, the payee cooling-off block (superseding the last sentence of #35), the first-time-payee sheet and the pay-flow XCUITest land now. Phase 5 keeps the Postgres row lock for the per-payer check (#61), asserting Payment-row anonymisation on account deletion (#36), the dark-mode and accessibility passes, and the go-live checklist. Invite shares a placeholder link until Phase 3 (#67).
70. **The bank is opened only after the first-time sheet has gone.** The TrueLayer SDK (and the web session) present on the top view controller, so tapping Pay on the sheet records the decision and authorisation starts from the sheet's dismissal callback; a dismissal after Pay never discards the created payment. Failure copy comes from the status, not the provider's `failure_reason` code (kept for support): cancelled and failed each have one sentence that the result screen and the payment detail share, so the wording never flips when the server catches up with the bank.
71. **Phase 2 review follow-ups.** The webhook verifier refetches the JWKS at most once a minute and only when a signature names a kid it does not hold (a flood of forged kids cannot turn into a flood of fetches), and requires `X-Tl-Webhook-Timestamp` to be covered by the signature. The fallback poll first looks two minutes after the last status change and then once per interval per payment, so a wedged provider does not get asked every minute about every payment. Buttons on a tinted result screen use an on-tint style (ink on the status colour) instead of the primary style, so contrast stays above 4.5:1 on every outcome. Contacts are read off the main actor. MockMode still cannot produce a Failed result (it would need a mock switch, e.g. a payee whose payments always fail); that goes with the Phase 5 polish list.
72. **Every request the app makes is a split.** The Request flow always creates a `Split`, even for one person, so progress, nudges and the shared link work the same way and the definition of done ("the split shows 1 of 1 paid") holds. `POST /requests` exists as SPEC 5 lists it and is tested, but the app does not call it. Requests go only to people on Quid, because `PaymentRequest.payerUserId` and `SplitShare.userId` are required; contacts not on Quid get an invite link instead. Paying from a web page without the app is the collection page's job (Phase 4).
73. **Split totals and shares.** `totalMinor` is the whole bill, each share is what one person is asked, and whatever the shares leave over is the creator's own part (`creatorShareMinor`). An equal split works in whole pence: when the creator is included they absorb the odd pennies, otherwise the first people asked pay a penny more. A share can be at most the per-payment limit (£250), since a request is paid in one payment; a split asks at most 20 people and describes at most £10,000. The payment reference comes from the title: accents folded, characters outside the Faster Payments set dropped, cut to 18, "Quid split" when nothing is left. Titles are at most 40 characters and notes 140, counted as people see them (one per emoji or flag), the same count the app's field shows. The requester needs a verified account outside its cooling-off window, otherwise nobody could pay them; the people asked need no bank account. Creating requests and splits shares one budget of 20 a minute per user.
74. **Paying a request.** `POST /payments { requestId }` takes the payee, amount and reference from the request; `amountMinor`, when sent, must match, the payer must be the person asked and the request must be open. Limits and payee rules apply as for any payment. More than one payment may be started for the same request (a cancelled attempt, then another); the first to reach EXECUTED marks the request PAID with its `paymentId`. A second one that also executes is an ordinary payment to the requester, the same double-approval risk as Phase 2's Try again. A request declined or expired while its payment was in flight still becomes PAID, because the money moved. Settlement runs from the state machine for every transition that leaves a payment EXECUTED or SETTLED, duplicates and stale events included, so a webhook retried after a crash between the two writes repairs the request. A payment the fallback poll moved to EXECUTED is not polled again, so every poll tick also settles any request whose payment left the bank in the last day but which is not PAID yet; it normally finds nothing.
75. **Request lifecycle.** PENDING ends as PAID, DECLINED or EXPIRED. Requests expire after 14 days: every read treats an open request past `expiresAt` as EXPIRED and an hourly sweep writes it. Only the person asked can decline; there is no requester cancel in v1 (the status enum has no CANCELLED), which goes on the Phase 5 list. Deleting an account moves every open request to or from that user to EXPIRED and clears their invite code.
76. **Reminders.** A nudge is allowed once per 24 hours per request, and the condition is part of the write, so two taps at once send one. The first nudge is allowed straight after creating: SPEC 7 rate-limits reminders, and creating a request already notifies. A refused nudge answers 429 `remind_too_soon` with `nextReminderAt`. `POST /splits/:id/remind`, not in SPEC 5, backs "Remind everyone unpaid" in one call and reports who was reminded and who was skipped and why. Reminder calls are capped at 30 a minute per user. Push stays a log line (`services/push.ts`) carrying ids only.
77. **Who sees what.** `GET /splits/:id` answers its creator only and 404 for everyone else, so a split's existence does not leak; someone asked sees their own request, which carries `splitId` and `splitTitle`. `GET /requests` (`role=incoming|outgoing`, `status=pending|all`, and `splitId` so a split link finds the viewer's own request however old it is), `GET /requests/:id` and `GET /splits` are additions to SPEC 5 that Home, Activity and links need. Requester and payer see the same request fields.
78. **Invite and split links.** Each user has one stable invite code (8 characters, no look-alike letters or digits), created by the first `GET /me/invite`. `https://<domain>/i/<code>` shows the inviter's first name and either `APP_DOWNLOAD_URL` or a line saying Quid is not in the App Store yet. A split's link `https://<domain>/s/<id>` shows the creator's first name and the split's title, with no amounts and no other names, and an "Open in Quid" button to `quid://split/<id>`; the app opens the split for its creator and the request in it for someone asked. Both pages send no-store, no-referrer and a script-free CSP, and are capped at 60 a minute per IP. The shared https link opens the app directly only once universal links are set up in Phase 5; until then the page's button does it.
79. **Request flow details.** The picker ticks people on Quid. "Split equally" uses the keypad and an "Include me" switch that is off by default, so asking one person for £10 asks for £10; "Custom amounts" gives each person a decimal field. A title is required. "Split this with others" after a paid payment prefills the amount with Include me on, and the reference as the title unless it is the default "From <name>". Paying a request reuses the Pay flow with the amount and reference fixed and no keypad; Decline asks for confirmation. Activity gains a Requests filter with the user's splits and the requests addressed to them. In MockMode Priya pays her share five seconds after a split is created, so the demo shows a split filling up, and a fixture split shows a paid, a declined and a nudgeable share.
80. **Dates in server sentences are UK time.** Messages the app shows as they are (cooling-off, next nudge) read "Wed 21 Oct, 14:05" in Europe/London instead of an ISO timestamp; the ISO value stays in `details` for the app. This also changes Phase 2's `payee_cooling_off` message.
81. **Organisations.** An organisation has one account, checked with Confirmation of Payee exactly like a personal one: only MATCH creates anything and CLOSE_MATCH returns the bank's version of the name to confirm. The details are stored encrypted under the organisation's own key (`org:<id>`), with no user attached. The creator becomes treasurer; one user can look after up to 10 organisations. There is no change-account endpoint in v1, so there is no cooling-off for organisations. Only treasurers get `OrgMember` rows, and `GET /orgs` lists the organisations the user looks after; the people asked to pay are `CollectionMember` rows.
82. **Collections.** A title of up to 60 characters, an amount each of at most £250 (it is paid in one payment), an optional due date from today to a year ahead, and up to 200 people: people on Quid, named as Quid knows them, and others by name. The slug is 8 characters with no look-alikes, and the link is `https://<domain>/c/<slug>`. `POST /collections/:id/close`, not in SPEC 5, stops new payments from the link and the app; payments already at the bank still count. There is no reopen in v1.
83. **Who a collection payment counts for.** An app payer's member row is chosen when the payment starts: they must be on the list and unpaid. Someone paying from the link is matched when the payment executes, to an unpaid member with the same name (ignoring case and spacing), or added as a new paid member. So an abandoned link payment leaves no row behind, two payments under one name show twice, and paying under someone else's name marks that row paid. A payment for a member who is already paid (two attempts that both went through, or a link payment under their name first) gets its own paid row, so money that arrived is never missing from the list. The phone number on the page is required, although SPEC 5 marks it optional, because SPEC 6 says TrueLayer needs `user.phone_number` for non-regulated clients and a payment without it would fail at the bank's step. It goes only to the payment provider. It is never stored and never used to match, because matching by number would let anyone with the link find out whether a number had paid. As for requests, every poll tick settles collection payments whose member write was lost.
84. **Collection reminders.** Once per 24 hours per member, with the condition in the write. People added by name have no way to be reached and are reported as `not_on_quid`, so the app says to send them the link. The limit is 30 reminder calls a minute per user. Push stays a log line.
85. **The public pay page.** `GET /c/:slug` answers JSON when the request asks for JSON and the pay page otherwise. The JSON is exactly `title`, `amountPerPersonMinor` and `organisationName`; a closed collection answers 410 and an unknown one 404. `POST /c/:slug/pay` takes JSON or the page's urlencoded form, parsed without a dependency, and answers `{ paymentId, authorisationUrl }` or a 303 straight to the bank's page; a problem shows the page again with the message and what was typed. Link payers are held only to the per-payment limit, which the amount already respects. The per-IP caps are generous because a whole club opens the page at once, often from one campus or mobile network address: 300 page loads and 60 payments a minute; the 8-character slug, not the cap, is what makes guessing links pointless. A browser that hits a cap gets a page saying to wait a minute, not JSON. The page's CSP leaves `form-action` open because the form's answer redirects to the bank's host; otherwise it is like the other public pages: no scripts, no framing, no caching, no referrer. The bank returns people to `/c/return?payment_id=<provider id>`, which shows only the status, amount, title and organisation name. It refreshes every 3 seconds while pending, for about two minutes, from its own bucket of 600 a minute per IP, then says it is still waiting and stops. The fake bank returns there the same way (see #59 for what is unverified).
86. **Paying a collection from the app.** `POST /payments { collectionId }` is for people on the list. `amountMinor`, when sent, must match, the payer's own limits apply, and the reference is the title. The first-time warning shows when the payer has never completed a payment to that organisation, with the name the bank holds, which may be the treasurer's own. `GET /collections/due`, not in SPEC 5, lists the collections the user is on, for Home and Collect.
87. **Collect in the app.** The Collect tab shows "You're on the list" first, then each organisation the user looks after with a New collection button; the + menu also offers a new organisation. The treasurer view has a link card (Copy, Show QR, Share), the Unpaid / Paid / All filter, Remind per person, "Remind all unpaid" and Close behind the ⋯ menu, with a confirmation. QR codes are made on the phone with Core Image (error correction M), dark on white in both appearances so cameras read them. Paying a share, from Home or Collect, reuses the pay flow with the amount fixed. The "Phase N" placeholder sheet is gone. In MockMode, Sam looks after SOAS Hockey Club (Trip deposit, Kit order) and owes Flat 4B's October bills; in a collection created in the demo, anyone called Priya Patel pays after five seconds.
88. **Seed data.** `npm run seed` makes Sam treasurer of SOAS Hockey Club (its fixture account matches) with an open Trip deposit, and gives Priya's Flat 4B an October bills collection that Sam is on.
89. **Account deletion and Collect.** Deleting an account also takes the user off every collection list: the rows keep their place and paid state but lose the link to the account and become "Deleted user", so they are no longer on Quid and can't be reminded. Their treasurer roles end, and an organisation left with no treasurer has its open collections closed, since nobody could see or manage them. Handing an organisation over to another treasurer, and deleting an organisation with its account, are on the Phase 5 list.
90. **Forms post urlencoded bodies everywhere.** The parser for `application/x-www-form-urlencoded` is registered for the whole app, not only the collection page. The dev bank's Approve and Decline buttons post an empty form body, which a browser sends with that type; before Phase 4 the dev routes had no parser for it and answered 415, which broke the fake-bank loop in a real browser (Phase 2, found in the Phase 4 review).

## Phase 5

91. **Requesters can withdraw requests.** `RequestStatus` gains CANCELLED (and `PaymentRequest.cancelledAt`), superseding the last part of #75. `POST /requests/:id/cancel` withdraws one open request and `POST /splits/:id/cancel` every open share of a split; neither is in SPEC 5. Only the requester can, only while the request is open and unexpired, and the condition is part of the write; paid, declined and expired shares are left alone, and a split with nothing open answers 409 `split_nothing_to_cancel`. The payer gets a push stub and sees "Cancelled"; paying, declining or nudging it answers `request_not_pending` with "This request was cancelled." A payment already at the bank still pays a cancelled request when it executes (#74), because the money moved. In the app, every request is a split (#72), so the split's ⋯ menu offers "Cancel open requests" with a confirmation; a split whose every share was withdrawn reads Cancelled instead of Done. App builds from before this change can't decode a CANCELLED request; none have been released.
92. **Payers can cancel a payment they haven't finished.** `POST /payments/:id/cancel` (payer only, not in SPEC 5) asks the provider to cancel, then reads the payment back and applies what the provider says, so our row becomes CANCELLED only once the provider confirms and a payment the bank executed anyway is never marked cancelled (it answers 409 `payment_not_cancellable`). TrueLayer's cancel is asynchronous (#59): when the read-back still shows it in flight, the webhook or the fallback poll applies the cancellation. Once the payer has approved at the bank (AUTHORIZED) the bank is sending it, so the endpoint answers 409 without asking the provider. A 4xx from the provider is followed by the same read-back and trusted only when that shows the payment approved or ended; a refusal of a payment still waiting for the payer means our cancel call itself is wrong (#59) or rate-limited, so it logs a warning with the provider's status and code and answers 502 rather than pretending. Anything else answers 502 and changes nothing. A row the provider never saw answers 409 `payment_starting`, and the abandoned-creation sweep (#61) still covers it. The fake provider refuses a cancel after approval, and a failed fake payment never moves on, as a real bank's wouldn't. If a provider ever reports money sent for a payment we closed as failed or cancelled, the state machine keeps our status but logs an error tagged `sent_after_failure`, because that needs a person (a refund or a fix). The app calls the endpoint when the first-time sheet is cancelled (without waiting) and whenever the bank step ends without completing (cancelled, or the bank's page failed), so the amount stops counting against the payer's limits straight away; the bank's own failure sentence stays on the result screen; this replaces "left to expire" in #66. Calls share the payment-creation rate limit. One sentence covers both cancels, "You cancelled the payment. Nothing has been sent.", on the result screen and in the payment's detail (#70).
93. **At most 10 new payees a day.** Each first payment to someone returns their bank-held name (#63), so a payer can start paying at most `LIMITS.newPayeesPer24h` (10) distinct new people in a rolling 24 hours; the eleventh answers 429 `new_payee_limit`. `Payment.firstTimePayee` records which payments disclosed a name, and they count whatever became of the payment afterwards, since the name was shown. Trying the same new person again the same day costs nothing more, and people paid before never count. Collection payments are flagged and audited too but not capped: the payer has to be on the list, and the name is the organisation's account. A start the provider refused (502, `provider_error`) or that never reached it (`abandoned`) showed no name and doesn't count. Every disclosure writes an info line `first-time payee name disclosed` with `audit: "payee_name_disclosed"`, the payment id, the payer id and the payee user or organisation id; never the name.
94. **Universal links, ready but off.** `GET /.well-known/apple-app-site-association` serves `applinks` for the app ids in `APPLE_APP_IDS` (`<Team ID>.<bundle id>`, validated at startup), claiming `/s/*` only; it answers 404 while none is set. Invite links and collection pages stay in the browser, because the people they are for may not have the app and the collection page is how anyone pays without it. The app already opens `https://<domain>/s/<id>` (#78). Its Associated Domains entitlement is a template, `ios/Config/AssociatedDomains.entitlements`, not wired into the target: the capability needs a paid Apple Developer team and a personal team cannot sign it, which would stop anyone running the app on a device with a free account. Turning it on is three steps in the go-live checklist.
95. **The schema is tested on Postgres in CI; one instance in production.** A second backend job runs the whole suite against Postgres 16 with only the datasource provider changed (#1), pushing the schema because the committed migrations are SQLite SQL. The test setup uses a plain `prisma db push` on a new database: Prisma refuses `--force-reset` when an AI agent runs it, and each test file empties its tables anyway. Going live on Postgres needs a Postgres baseline migration (go-live checklist). The keyed locks, rate-limit counters, poll and sweeps are in-process, so production runs exactly one instance; the advisory-lock change needed to scale out is on the checklist rather than built, which replaces the "row lock" note in #61.
96. **Contrast is a test, in both appearances.** Colour tokens are defined once as UIKit dynamic colours (`QuidPalette`), which the SwiftUI tokens wrap, so `DesignSystemTests` resolves each one in light and dark and checks every text-on-fill pair the screens draw at 4.5:1 or more, plus the six avatar tints. The only token pair under 4.5:1, muted text on the pressed secondary fill (4.32:1 in light), is not drawn anywhere: secondary buttons are labelled in ink. Disabled controls (45% opacity) are exempt, as WCAG allows. `-dark-mode` and `-light-mode` launch arguments force an appearance for tests and screenshots.
97. **Accessibility audit.** `AccessibilityAuditTests` runs `performAccessibilityAudit` over Home, Activity (and its Requests filter), a split, Collect, a collection, Me, the pay picker, the amount screen and the result, and the request picker, in light, dark and the largest accessibility text size. Every finding prints an `AXAUDIT|variant|screen|type|description|element` line that CI collects. The first run, in report mode, found 259 issues (104 light, 102 dark, 53 at the largest size). The real ones are fixed: paid collection shares were disabled buttons, which SwiftUI dimmed below 4.5:1, and are plain rows now; avatars grow with the text size (ScaledMetric) instead of squeezing their initials; row names and subtitles wrap at accessibility sizes instead of truncating (`quidLineLimit`); link addresses carry a VoiceOver label and are no longer tiny selectable targets; amounts have spoken labels ("12 pounds 50"); the bank row's thin outline icon became the filled one; and the test now waits for each screen's content instead of auditing its loading placeholders. Every remaining finding fails the test except five documented kinds, which are printed with their reason: anything under the tab bar, a pinned bottom bar or the navigation bar (measured against the bar's material and the scroll-edge effect, not against what a person sees once it is scrolled into view); disabled controls (exempt in WCAG); Dynamic Type on bar buttons (UIKit keeps bar items at bar size and offers the Large Content Viewer) and on avatar initials (which grow with their circle); text clipping, reported for single-line SwiftUI text that fits, so it stays in the log for review rather than failing; and "potentially inaccessible text" with no element, which is the avatar initials hidden from VoiceOver on purpose because each row reads the full name. Apart from the link address, the audit found no target under 44 points and no unlabelled button.
98. **MockMode payments wait for the mock bank, and some fail.** A mock payment stays AUTHORIZING until the mock bank approves it (`MockPaymentAuthoriser` with a completed outcome), then turns Paid about two seconds later; before, it moved on a timer from creation, so a payment whose first-time sheet was cancelled still showed as paid a few seconds later. Any amount ending in 13p is declined by the mock bank and ends FAILED, so the Failed result and Try again can be seen and tested, which closes the MockMode gap in #71. Cancels work as on the server.
99. **Account deletion, asserted end to end.** The Phase 1 deletion (#36) is now tested with payments in place: the other person's history keeps the payment with its amount and status, shown to "Deleted user"; the deleted row has no phone number, hash or invite code; bank details and sessions are gone and the old token answers 401; open requests to and from them are closed; nothing the other person can fetch contains the deleted user's name, number or account. Handing an organisation to another treasurer and deleting an organisation (#89) are not built in v1 and are listed as such in the runbook.
100. **Pay-flow UI tests in MockMode.** Paying a known payee to Paid (Phase 2), the first-time warning with the bank-held name, its Cancel (back to the amount, nothing sent) and then Pay to Paid, and a payment the bank declines showing Failed with Try again keeping the person and amount. Unit tests cover the cancel calls made from the sheet and from the bank's cancel.
101. **Release builds still read two settings from the scheme.** Writing the go-live checklist showed that `AppConfig` reads `QUID_API_BASE_URL` and `QUID_TRUELAYER_ENV` from the scheme's environment variables, which a TestFlight or App Store build doesn't have, so a release build would talk to `localhost:3000` and the sandbox. Left as is for v1 (only simulator and Xcode runs exist) and on the go-live checklist: both become Info.plist keys set per build configuration.
